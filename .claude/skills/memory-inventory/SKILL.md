# auto memory の棚卸し

auto memory を、**ユーザーの合意を取りながら**整理するスキル。

標準の `consolidate-memory` は Claude の自己判断で統合・削除まで実行する。
このスキルはそこを置き換える。判断が要る操作は必ず合意を取り、
不可逆な削除は行わず `_archive/` への退避に置き換える。

## 前提知識

- 毎セッション読まれるのは **MEMORY.md のみ**（先頭 200 行 or 25KB の早い方）
- トピックファイルは起動時に読まれない。MEMORY.md のフック文が**唯一の入口**
- したがって棚卸しの主対象は **MEMORY.md**。トピックファイルの多少の散らかりは実害が小さい
- `~/.claude/projects/` は gitignore 済みで **git 履歴がない**。誤削除は復旧できない

## 設計原則

1. **目次を正確で短く保つことが目的**。件数を減らすことではない
2. **削除しない**。廃止は `_archive/` へ `mv`（トピックファイルは起動時に読まれないため退避コストはゼロ）
3. **承認レベルを分ける**。全部聞くと苦痛、全部黙ってやると事故る
4. **カテゴリ単位で聞く**。ファイル単位では AskUserQuestion の上限（1 回 4 問）に収まらない

## 承認レベル

| 操作 | 承認 | 理由 |
|:--|:--|:--|
| 目次の圧縮（詳細をトピックファイルへ移動） | 不要（事後報告） | 情報が失われない |
| 事実の修正（gh 等で検証済みのもの） | 不要（事後報告） | 根拠が客観的 |
| `_archive/` への退避 | カテゴリ単位で一括確認 | 可逆 |
| ファイルの統合・本文の削除・書き換え | **必須** | 不可逆で内容が失われる |

## Phase 0 — バックアップ

memory ディレクトリを特定し、実行前にバックアップを取る。

```bash
MEM_DIR=$(ls -d ~/.claude/projects/*$(basename $(git rev-parse --show-toplevel 2>/dev/null || pwd))*/memory 2>/dev/null | head -1)
cp -r "$MEM_DIR" ~/memory-backup-$(date +%Y%m%d-%H%M%S)
```

特定に失敗したら、ユーザーにパスを確認する。推測で進めない。

## Phase 1 — 実測

数字を出す。印象で語らない。

- MEMORY.md の**行数・バイト数**（上限 200 行 / 25KB に対する使用率）
- **1 行あたり平均バイト数**（推奨は 1 件 150 文字以内）
- ファイル件数と合計サイズ
- `type` の分布（`user` / `feedback` / `project` / `reference`）
- `modified` frontmatter が**無い**ファイル（v2.1.214 以前から未更新 = 古さの目安）
- MEMORY.md から参照されていない**孤児ファイル**
- MEMORY.md に載っているが**実体が無い**リンク切れ
- **中身が薄いファイル**（本文が数行しかない / `Why` と `How to apply` が無い）→ 他へ畳めないか

```bash
cd "$MEM_DIR"
echo "MEMORY.md: $(wc -l < MEMORY.md) 行 / $(wc -c < MEMORY.md) bytes"
awk '/^  type:/{print $2}' *.md | sort | uniq -c | sort -rn
grep -L 'modified:' *.md
for f in *.md; do [ "$f" = MEMORY.md ] && continue; grep -q "$f" MEMORY.md || echo "孤児: $f"; done
```

## Phase 2 — 鮮度検証

**ここが本体。** 記憶の内容を鵜呑みにせず、外部の事実と突き合わせる。

- **PR / issue 番号**を含む記述 → `gh pr view <n> --json state,mergedAt` / `gh issue view <n> --json state` で状態確認
- **「◯◯までは注意」「マージ前に実施」型の条件付き記述** → 解除条件が満たされていないか最優先で確認。
  これが目次に残っていると毎セッション誤った前提を私に与える
- **ファイル・関数・フラグ名**への言及 → 実体がまだ存在するか確認
- **相対日付**（「来週」「今月中」）→ 絶対日付に変換できるか

検証できなかったものは「未検証」として提案に明記する。検証済みと混ぜない。

## Phase 3 — 提案の組み立て

実測と検証結果を、**判断の性質ごと**にカテゴリへまとめる。ファイル単位で並べない。

典型的なカテゴリ:

- **事実誤り** — 検証で誤りが確定したもの（承認不要だが提示はする）
- **役割を終えた記録** — 完了した作業、決着した issue、期日が過ぎたもの → 退避候補
- **近接クラスタ** — 同じ話題の複数ファイル（例: drizzle 系 3 件）→ 統合候補
- **目次の肥大** — 150 文字を超えるフック行 → 圧縮候補
- **再取得可能** — コード・git 履歴・issue・CLAUDE.md を見れば分かることを書いているだけのもの → 削除候補
- **rules 向き** — 特定のファイルやディレクトリに紐づく技術的な地雷で、チームの誰が触っても踏むもの → `.claude/rules/` への移行候補
- **中身が薄い** — 本文が数行で、単独のファイルである必要が無いもの → 他へ畳む候補

**再取得可能かどうかの線引き**: 引き直せるもの（ディレクトリ構成、依存関係、過去の修正内容）は削る。
引き直せないもの（ユーザーが明言した好み、その判断に至った経緯、誰に聞けばいいか、実測して初めて分かった罠）は残す。

`project` には「進行中の状態」と「恒久的な知見」が混ざりやすい。
前者は決着すれば不要になり、後者は 1 年後も有効。ここを分けておくと次回以降の判断が楽になる。
なお恒久的な技術知見の置き場は `project` のままでよい（`reference` は外部リソースへのポインタを指す型なので、
そこへ移すのは定義に反する）。

## Phase 4 — 合意（AskUserQuestion）

**1 ラウンド最大 4 問**。カテゴリごとに 1 問。選択肢は 2〜4 個。

各問には「一括で実行」「個別に見る」「やらない」を基本に据え、
`description` に**対象件数と代表的なファイル名**を書く。ダイアログ上ではラベルしか見えないため、
判断に必要な情報は description に寄せる。

「個別に見る」が選ばれたカテゴリは、次のラウンドで内訳を提示して再度問う。
カテゴリが 4 個を超える場合は、**影響の大きい順**にラウンドを分ける。目次に関わるものが最優先。

質問の前に、そのラウンドで扱うカテゴリの根拠をチャット本文に簡潔に書く。
ダイアログだけで判断させない。

## Phase 5 — 反映

合意された範囲のみ実行する。承認レベル表に従う。

**退避:**

```bash
mkdir -p "$MEM_DIR/_archive"
mv "$MEM_DIR/<file>.md" "$MEM_DIR/_archive/"
```

退避したら **MEMORY.md から該当行を削除**する。ファイルを動かすだけでは目次に残り、リンク切れになる。

退避する前に、**そのファイルに残っている恒久的な教訓を、生き残る側のファイルへ畳んでおく**。
記録そのものは役目を終えていても、そこで学んだことは残ることがある。

**統合:**

2 ファイルを 1 つにまとめるときは、**内容が厚い側のパスを残す**。薄い側を吸収させて退避する。
被リンク（`[[name]]`）が残らないよう、他のファイルからの参照も張り替える。

**相対日付の変換:**

「来週」「今月中」「マージ後」のような相対表現を見つけたら、**絶対日付に書き換える**。
書き換えられない（基準が不明な）場合は、その旨をレポートに書く。

**目次の圧縮:**

1 件 1 行、150 文字以内、`- [Title](file.md) — 一行フック` の形式。
削った詳細は**必ずトピックファイル側へ移す**。捨てない。

フックは「何が書いてあるか」ではなく「**どういう時に開くべきか**」を書く。
私はこの一行だけを見てファイルを開くか判断する。
近い話題のファイルが並ぶときは、**発動条件で書き分ける**（「実行する前に」「実行した後に CI が落ちたら」）。
内容を要約すると似た話題は似たフックになり、取り違える。

削るだけでなく、**新しく重要になったものを目次に足す**。
セッション中に追加されたトピックファイルが目次に載っていない場合、それは孤児として永久に開かれない。

**上限チェック:**

書き終えたら MEMORY.md を再計測し、200 行 / 25KB に収まっているか確認する。
超過分は次回ロード時に黙って捨てられる。

## Phase 6 — 報告

- 触ったファイル数と、操作の内訳（修正 / 圧縮 / 退避 / 統合）
- MEMORY.md の **before / after**（行数・バイト数・使用率）
- **合意が得られず見送った項目**を明示する。黙って落とさない
- 未検証のまま残した項目

## 実行頻度の目安

毎回このスキルを打つ必要はない。

- **主: イベント駆動** — PR マージ / issue クローズ時に、該当する記憶をその場で直す。
  「◯◯まで注意」型はここで消えるのが理想
- **従: 月 1 回、または新規・更新が 15 件たまったら** — 上から漏れたものを拾う
- **随時: MEMORY.md が 15KB（上限の 6 割）を超えたら** — 件数に関係なく実行

毎日は過剰。書き込みの無い日にかけると、同じ内容が繰り返し再圧縮され、
**具体的で再導出しにくい記述から先に失われる**。

## やってはいけないこと

- 合意なしにファイルを削除する（`rm` を使わない。退避は `mv`）
- 検証していない推測を「確認済み」として提示する
- 目次を短くするために、トピックファイルへ移さず詳細を捨てる
- カテゴリをまたいで「まとめて全部やっていいか」と一問で聞く（判断の粒度が潰れる）
