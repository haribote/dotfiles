# helper-agent へのプロンプト雛形

helper-agent は fresh context で起動する（このセッションの会話を引き継がない）。担当範囲・前提・完了条件を漏れなく書く。以下の雛形を土台に、リポジトリとタスクに合わせて埋める。

```
あなたは <リポジトリ名> の <タスクの種類> を1本、worktree の中で完結させる helper-agent です。
このセッションは lead-agent が起動しました。作業対象・完了条件は以下だけです。範囲外のファイルには触れないでください。

## 担当
- 対象ファイル: {FILE_PATH}
- ブランチ: {BRANCH}（作成済み、worktree 内で作業中、カレントディレクトリがそのworktree）
- 一次ソース: {ISSUE_OR_SPEC_REFERENCE}（issue番号、チケット、設計文書など。参照方法も書く）

## 修正内容
{具体的な変更内容。何を、なぜ変えるか。曖昧にすると helper-agent が独自解釈で範囲を広げる}

## 前提として読むもの
- {対象ファイル自体の現状}
- {依存する上流ファイル・仕様。並行実行中の他のブランチではなく、最新 main を読ませる}
- {リポジトリのコーディング規約・設計規約があれば}

## 対応不要（他の担当）
- {並行実行中の他の helper-agent が担当しているファイル・領域を明記し、触れないよう指示する}

## 厳守事項
1. {リポジトリのコーディング規約・文体規約があれば、それに従うことを明記}
2. コミットメッセージの規約（形式・言語）
3. **作業中に独立した機械的サブタスク（複数ファイルの調査・grep・要約・定型変換など）が見えたら、`/tewake` skill の基準に従い、軽量モデルのサブエージェントへの委譲を検討すること。** あなた自身も lead-agent と同じくオーケストレーションに徹する場面がある。
4. **draft PR を先に出す**: 最初のコミットを push した直後に `gh pr create --draft --title "..." --body "WIP" --base main` で番号を確定させる。番号が要る記述（更新履歴等）がある場合は、確定後に書き戻す。
5. 仕上がったら `gh pr ready <番号>` を実行する。
6. {ビルド・テスト・lint コマンド} をローカルで実行し、このPRの範囲でエラーが出ないことを確認する。
7. 新たに担当外のファイルに矛盾を見つけたら、修正はせず {申し送り先。issueコメント等} に記録すること。
8. 完了したら、変更したファイル一覧・PR番号・検証結果を短く報告して終了する。**merge は行わない**（lead-agent の担当）。

作業を始めてください。
```

## 埋め込み変数のコツ

- **担当ファイルは narrow に絞る**。「このファイルとこのファイルだけ」を明記し、隣接ファイルへの言及があっても触れないよう釘を刺す。並行実行では同じファイルを2つの helper-agent が触ると衝突する。
- **一次ソースは「読み方」まで書く**。issue のコメント欄を読ませたいなら `gh issue view <番号> --comments` のようなコマンドまで書く。ファイルパスだけでは見落とされる。
- **依存文書は「最新 main を読む」と明記する**。helper-agent は自分の worktree のブランチ作成時点のスナップショットで作業を始めるが、並行 Wave の他の PR が先に merge されている場合、その内容は worktree のベースブランチには反映されていない。明示的に fetch / rebase させるか、依存が薄い場合は無視してよいと伝える。
- **「対応不要」の範囲を具体的に書く**。他の並行 helper-agent が触っているファイル名を名指しすることで、境界の踏み越えを防ぐ。
- **完了条件を機械的に確認可能な形にする**：「エラーが出ないこと」ではなく「`npm run <check-command>` の exit code が 0 であること」のように、helper-agent が自己判定できる基準を渡す。
- **merge しないことを明記する**。書かないと自律的に merge しようとすることがある。

## レビュー対応の追加プロンプト（2周目以降）

code review で指摘が出たら、以下の形で追加のプロンプトを送る（同一 pane・同一 helper-agent に継続で送ってよい、fresh context に戻す必要はない）。

```
code-review で {N} 件の指摘がありました。

**修正が必要（同一ファイル・改訂範囲内）**：
{指摘の内容。ファイル・行番号・何が問題か・どう直すべきかを具体的に}

**対応不要、申し送りのみ（別ファイル）**：
{ファイル名・内容}。修正はせず {申し送り先} へ記録してください（前回の記録と重複しないか確認してから）。

修正後、コミット・push・{検証コマンド} の確認まで行い、報告してください。
```

指摘が2〜3周を超えて同じ根本原因を繰り返すようなら、`references/troubleshooting.md` の「レビューの発散を防ぐ」に従い、それ以上の追加プロンプトは送らず打ち切る。
