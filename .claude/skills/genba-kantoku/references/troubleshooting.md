# 実務トラブルシューティング

## `herdr agent wait --until done` の `done` が誤検知することがある

helper-agent が重いコマンド（テスト実行など）をバックグラウンドで実行し、完了通知を待っている最中でも、herdr 側はターンが一旦区切られたタイミングで `agent_status: done` を返すことがある。実際にはまだ作業途中。

`done` を受け取って `herdr pane read` で pane 内容を確認したときに「まだ実行中」「完了通知を待っています」といった表示が続いている場合は、lead-agent 側で直接プロセスの有無を確認する：

```bash
ps aux | grep <対象コマンド> | grep -v grep
```

プロセスが生きていれば、追加の `herdr agent wait <name> --until done --until blocked --timeout <長め>` で待ち直す。それでも動かない場合は、`herdr agent prompt <name> "状況を確認して報告してください"` のように明示的に催促する。

## helper-agent が公開操作の前に確認プロンプトを出すことがある

`--permission-mode auto` で起動していても、`gh issue comment`・`gh pr comment` のような「可視化される公開操作」の前に、helper-agent 自身が選択式の確認を挟むことがある（auto mode の分類器が一段階止める模様）。

pane を読んで選択肢が出ていたら、lead-agent が番号で応答する：

```bash
herdr agent prompt <name> "2" --wait --until done --until blocked --timeout 120000
```

「内容を見せてほしい」を選び、投稿前に文面を確認してから「この内容で投稿する」を選ぶ2段階にすると安全。

## draft PR 作成直後に push し忘れることがある

「更新履歴に PR 番号を書き戻す」のような、PR 番号確定後の追加コミットを作らせる場合、helper-agent がコミットだけして push を忘れることがある。CI が古いコミットのまま失敗するので、CI 失敗時はまず対象ブランチの ahead/behind を確認する：

```bash
git -C <worktree-path> status
```

`Your branch is ahead of 'origin/<branch>' by N commits` と出ていたら push し忘れ。追加プロンプトで push を促す。

## レビューの発散を防ぐ

設計文書・スキーマ・型定義など相互参照が密な対象では、1つの変更が code review のたびに芋づる式に他ファイルとの食い違いを見つけ続ける。全部その場で直そうとすると、当初の PR 分割が意味を失い、1つの PR が際限なく肥大化する。

運用パターン：

1. code review の指摘を「同一ファイル内・その PR の改訂範囲」と「別ファイル」に分類する。
2. 同一ファイル内のみ修正し、別ファイルへの指摘は申し送り先（issue コメント等）に記録する。重複投稿を避けるため、投稿前に既存の申し送りを確認させる。
3. 修正 → CI 再確認 → 再度 code review を1回だけ回す。新規性のある指摘（前回と同型でない）が出たら同じ基準でもう1回だけ対応し、それ以降は申し送りのみに切り替えて打ち切る。
4. 「発散」の兆候（同じ根本原因の指摘が繰り返し出る、別ファイルへの言及ばかりになる）が出たら、ユーザーの指示を待たず lead-agent の判断で打ち切ってよい。ただし、大きな設計判断（アーキテクチャの前提が崩れているなど）が絡む場合は打ち切る前に一度ユーザーに状況を報告する。

## 後続の作業で前の作業の誤りが発覚する

並行実行を何ラウンドか回すと、「後の PR のレビューで、既に merge 済みの前の PR 自体の誤りが見つかる」ことがある。特に、複数ファイルが同じ性質（例：実装済みの値だけを反映する早見表、生成されたコードなど）を持つ場合、そのうち1つを直したときに初めて「他のファイルも同じ誤りを踏んでいた」と気づくパターンが多い。

見つけたら、その場で手を広げて直しにいかず：

1. 何が起きているかを整理する（どのファイルが、どんな前提の食い違いを持っているか）。
2. lead-agent としてユーザーに報告し、対応方針を確認する（今回のスコープに含めるか、新しい Wave / PR を追加するか、申し送りに留めるか）。
3. 方針が決まってから、必要なら新しい worktree・helper-agent を立てて対応する。

これは並行作業の副産物として珍しくなく、慌てて手を広げるよりも一度立ち止まって俯瞰する方が、結果的に手戻りが少ない。

## worktree 環境のセットアップ漏れ

git worktree は `node_modules`（や同種の依存ディレクトリ）を共有しない。各 worktree で依存関係インストール（`npm ci` 等）を必ず実行してから helper-agent を起動する。symlink で使い回そうとすると、`git add -A` が意図せず巻き込んでコミットに混入することがあるので避ける。

## SSH 鍵の署名でパスフレーズが求められる

git commit の署名（GPG/SSH signing）で helper-agent がパスフレーズを要求されることがある。これは秘密情報なので lead-agent も helper-agent も代行できない。ユーザーに `ssh-add <鍵のパス>` を実行してもらう（`!` プレフィックスでこのセッションから直接実行を依頼できる環境なら、それを使うとよい）。ssh-agent への登録は通常マシン全体に効くため、以降の worktree では再入力不要になる。
