# 手分け（軽量サブエージェントへの委譲判断）

メインエージェントはオーケストレーションに徹し、判断力を要さない作業は軽量モデル（haiku 等）のサブエージェントに委譲する。これにより、メインエージェントの文脈は調整と統合に集中でき、独立した作業は並列に進む。

このスキルは「委譲するかどうか・どのモデル階層に委譲するか」の判断基準を扱う。並列実行そのものの型（複数の独立タスクをどう同時に走らせるか）は `dispatching-parallel-agents` スキルに従う。両者は組み合わせて使う。

## いつ検討するか

タスクに着手する前、および作業の途中で新しいサブタスクが見えたときに、都度「これは軽量モデルに落とせないか」を検討する。複数タスクが並んでいるときだけでなく、**一見単一に見える複雑なタスクでも、機械的な部分を切り出して委譲できないか**を考える。

## 規模とオーバーヘッドを踏まえる

委譲にはサブエージェントの起動・待機・出力検証というコストが伴う。作業内容が「軽量モデル向き」に見えても、単一のコマンド（`rg` 一発など）や数手で完結する規模なら、委譲せず自分で直接実行した方が速い。委譲を検討するのは、対象が複数ファイル・複数対象にまたがる、逐次実行では時間がかかる、あるいは並列化によって明確に短縮できる規模のときに限る。判断や設計が絡むタスクの下準備として調査を切り出す場合も同様で、切り出す調査自体が小規模なら、無理に分離せずメインエージェントが直接調べた方がよい。

## 軽量モデルへの委譲に向くタスク

以下のような、正解が一意に決まりやすく、深い判断や曖昧な意図の解釈を必要としない作業は軽量モデルに向く。

- 複数ファイル・複数ディレクトリにまたがる機械的な調査（grep、ファイル特定、該当箇所の列挙）
- 定型的な要約・抽出・変換（フォーマット変換、単純な集計、既知パターンへの当てはめ）
- 同種の作業を多数の対象（ファイル、レコード、PR など）に反復適用する作業
- 独立したチェック・分類（lint 結果の分類、ログのカテゴライズ、単純な検証）

## 軽量モデルに向かないタスク

以下は上位モデル（セッションのデフォルトモデル）にとどめる。無理に軽量モデルへ落とすと、誤った判断が後段に伝播し、統合コストがかえって増える。

- 設計判断・トレードオフの評価
- 曖昧な要求からユーザーの意図を推定する作業
- アーキテクチャ選定、セキュリティに関わる判断
- 複数の情報源・複数エージェントの結果を統合して結論を出す作業（これはメインエージェント自身が担う）

判断に迷うときは、「この作業の出力を検証せずにそのまま使ってよいか」を基準にする。検証なしでは危ういと感じるなら、上位モデルに残すか、委譲した上で統合前に自分で目視確認する。

## ツールの使い分け

- **Agent ツール**: 単発のサブタスクを委譲するときに使う。軽量モデルに落とす場合は `model` パラメータに明示的に `haiku` を指定する。省略するとセッションのモデルを継承するため、意図的に軽量モデルへ委譲したいときのみ指定する。
- **Workflow ツール**: 複数ステージにまたがる処理で、ステージごとにモデル階層を変えたいときに使う。`agent()` の `opts.model` / `opts.effort` で、機械的な収集・調査ステージは軽量モデル・低 effort、判断や検証を要するステージは上位モデルのまま、という組み合わせを設計する。

## 既存スキルとの役割分担

- `dispatching-parallel-agents`: 独立タスクを**並列に実行する型**（How）を扱う。
- **本スキル**: どのタスクを**軽量モデルに委譲すべきか**（Which）を判断する。
- `subagent-driven-development`: 実装計画をタスクごとにサブエージェントへ発注する開発フロー全体を扱う。

複数の独立タスクを軽量モデルに並列委譲する場面では、本スキルで委譲対象とモデル階層を決めたうえで、`dispatching-parallel-agents` の並列化の型に従って実行する。

## 委譲後の検証

軽量モデルは上位モデルより判断の精度が落ちやすい。委譲した結果をそのまま統合せず、以下を行う。

- 統合前に出力を目視確認する。特に外部に公開される成果物や、後続の判断の前提になる調査結果は要確認。
- 品質に疑問があれば、上位モデルへの再委譲か自分でのやり直しを検討する。
- 軽量モデルの出力を鵜呑みにして「委譲したので確認不要」とはしない。委譲は作業の分担であり、責任の移譲ではない。
